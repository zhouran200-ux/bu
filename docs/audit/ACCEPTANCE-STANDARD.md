# 个人使用 App 验收标准

审查基线：9c3df7b8002c429c487529b8195139c13bfe9c03。仅审查，不修改产品代码。

## 原则
1. 优先用户看得见的行为与真实数据风险，不按企业架构评分。
2. 问题必须有代码位置、触发条件、影响、最小修复建议。区分源码确认、静态推断、必须真机验收。
3. 文件长度、命名风格、零注释规则本身不构成缺陷；只有造成重复逻辑漂移、状态耦合、误修风险时提出拆分建议。
4. 不要求为个人应用引入服务器、复杂权限、多租户或全套分层；现有Room、Compose、协程机制能修则不引入新框架。

## 验收维度
- 正确性：模型选择/提示词/协议实际生效；引用不误跳；显示与真实配置一致。
- 数据可靠性：导入成功后可读取，删除范围正确，迁移不丢数据，保存失败不伪装成功。
- 交互一致性：确认、取消、返回、遮罩、横杠、列表滚动各有确定行为，连续操作不触发重复业务。
- 生命周期：切页/锁屏/后台/旋转/重建后状态合理，停止及时取消网络，服务与通知不残留。
- 性能与容量：长文导入/索引/提示词组装不过度阻塞UI，流式解析不无限重复，缓存与阅读记录有合理失效。不虚构耗时。
- 失败可恢复：网络断开、鉴权失败、空响应、模型无候选、格式损坏时清晰反馈，重试不会吞掉既有数据。
- 维护实用性：重复规则一致，测试覆盖危险边界，构建检查与实际用户约定一致。

## 优先级
P1：可能误删/丢失用户数据、定位错误证据、核心生成不可用或无法停止，优先处理。
P2：可复現的交互/状态错误、长文明显高复杂度或主线程重计算、失败后无法合理恢复，应近期修。
P3：有明确实际收益但不阻断使用的小改进，等关联功能修改时处理。
不采用无关紧要的风格告警凑数量。

## 用户旅程
首次启动→新建笔记本→空资料聊天→导入TXT/DOC/DOCX→长文阅读→配置API/获取模型→选择方案模型→连续流式问答→停止/重生成→切页/返回/后台→引用原文→编辑资料→旧引用失效→删除笔记本/消息→重新启动→应用更新。

## 覆盖与证据
分模块报告保留逐文件阅读清单，主报告汇总去重与优先级。单测/静态检查可作为补充，不能等同真机手势、无障碍、动画、内存压力或服务后台限制已验收。
